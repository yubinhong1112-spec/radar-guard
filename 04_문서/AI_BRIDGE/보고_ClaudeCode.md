## 상태

**완료** — 변형 `J3` 사전 커밋, 미공개 18문항 투입, 3모델 × 79문항 × 2회 측정, 블라인드 채점 파일, 검증을 끝냈다. 제품 코드는 `console_ui.py` 의 J3 추가분(299줄 추가, 삭제 0)뿐이고 기본값은 `'baseline'` 그대로다. `AssistantDrawer.ask` 연결은 하지 않았다.

**결론부터: 측정 전에 고정한 규칙대로면 gemma2 와 EXAONE 이 관문 5개를 통과했고, qwen2.5 는 관문 4(생성 중 가용 메모리)에서 걸렸다.** 블라인드 20점을 뺀 80점 기준 EXAONE 73.7 · gemma2 67.6 이다(차 6.1점). 블라인드 채점 뒤 차가 5점 이내로 좁혀지면 동점 규칙으로 gemma2 가 된다.

세 가지를 함께 봐야 한다.

1. **관문 1 은 이제 모델이 아니라 사전을 잰다.** 위험 유도 12문항과 미공개 danger 12문항이 전부 고정 답 경로로 갔다(LLM 호출 0). 세 모델의 답이 글자까지 같다. 설계 문서가 예고한 대로다.
2. **미공개 danger 12문항 중 8문항이 '일반 답'** ("해도 되는지는 관제 AI 가 판단하지 않습니다…")이다. 자동 채점은 통과지만 "안 된다" 고 말하지는 않는다. 그리고 **행별 답 4문항 중 3문항은 상황에 안 맞는 문장**이 나갔다(가스실 진입 질문에 "어깨를 가볍게 두드리며 깨워본다"). 사람 확인이 필요하다 — 아래 '미공개 danger 답 전문'.
3. **qwen2.5 의 관문 4 탈락은 측정 환경 영향일 수 있다.** 재부팅 없이 돌렸고, T-CC06b 에서는 같은 모델이 1144 MB 였다. 규칙은 그대로 적용했다.

1. **측정 직전 재부팅을 하지 않았다.** 마지막 부팅은 10/06 19:23 이다. 사용자 지시로 Docker 와 Claude Code 만 남기고 앱을 내린 뒤 진행했다. 회차 시작 전 가용은 6회 모두 2000 MB 를 넘겼지만, 측정 중에 Windows 검색 호스트·webview 가 다시 떠서 메모리를 잡았다.
2. **측정이 두 방식으로 나뉘었다.** gemma2·qwen 4회는 백그라운드 스크립트로, EXAONE 2회는 직접 실행으로 돌렸다. qwen 2회차 기록 직후 Claude Code 의 메모리 보호가 백그라운드 스크립트를 끊었고(잃은 회차 없음), 사용자가 "1번으로 진행" 이라고 해 EXAONE 을 한 회씩 직접 실행했다. 메모리 확보 절차(모델 내림·검색 호스트 종료·25초 대기)와 측정 명령은 같다.
