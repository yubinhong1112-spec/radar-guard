### 가설 검증 결과

1. **"keyword_free 0/6 의 원인은 라우팅" — 참.** R 만으로 정답 문서 적중이 0/6 → 6/6 이 됐다. `_event_for` 의 단어 목록이 원인이라는 것이 숫자로 확인됐다.
2. **그런데 문서를 찾아도 답이 좋아지지 않는다.** keyword_free 묶음 통과는 세 변형 모두 0/7 이다. 검색은 고쳐졌고 남은 병목은 2B 모델의 지시 이행력이다. 예 — KF-01("손이 말려 들어갔어", R+P): 매뉴얼 4건을 찾았는데 답은 `1. LLM 은 위험 판정·차단·경보 해제·전원 재투입을 실행하지 않는다 / 2. 확정 즉시조치와 ...` 로 **프롬프트의 안전 규칙을 조치 번호로 베껴 적었다.**
3. **"event_action 이 새는 원인은 프롬프트" — 부분적으로 참.** R+P 가 event_action 묶음을 4/12 → 7/12 로 올렸다. 그러나 같은 변경이 system_explain 을 10/11 → 1/11 로 무너뜨렸다. 원인은 분리 설계의 결함이다 — R 이 **모든** 질문에 매뉴얼을 붙이므로, "검색 결과가 있는 경우" 조건이 사실상 전체 문항에 걸리고, 시스템 질문도 `SYSTEM_CONTEXT` 가 빠진 v2 프롬프트를 받는다. 답할 근거가 사라진 것이다.
4. **out_of_scope 가 R+P 에서 1/6 까지 떨어진 것은 같은 원인이다.** "조치만 번호로" 지시에 매뉴얼은 있고 질문과 무관하니, 2B 모델이 **빈 번호만 찍는다.** OS-01·OS-05·OS-06 답 원문이 `1.  2.  3. ... 10.` 이다. 거절도 아니고 답도 아니다.

### 지연 분해 — 검색 절반, 모델 재적재 절반

p50 기준 (초). Ollama 응답의 `load_duration`·`prompt_eval_duration`·`eval_duration` 과 Ollama 밖 `search_sec` 를 문항마다 기록했다.

| 토막 | R | R+P | R+P+N | 무엇인가 |
|---|---|---|---|---|
| search_sec | 7.16 | 7.10 | 6.97 | 질문 임베딩(bge-m3) + pgvector. **R 이 추가한 비용** |
| load_duration | 8.97 | 8.54 | 8.39 | 모델 적재. bge-m3 ↔ gemma2 교대 재적재 |
| prompt_eval_duration | 8.58 | 7.01 | 7.05 | 프롬프트 처리 |
| eval_duration | 2.40 | 3.32 | 3.17 | 생성 |
| 전체(elapsed) | 22.26 | 20.75 | 19.88 | HTTP 왕복 |

기준선 7.6초 → R 22.3초, 증가분 약 14.7초다. **검색 약 7.2초와 모델 적재 약 9.0초가 거의 반반**이고, 둘의 합이 증가분보다 크다. 즉 기준선에도 적재 시간이 일부 있었다는 뜻인데, **1단계 측정에는 `load_duration` 기록이 없어 정확한 귀속을 못 했다.** 그래서 분해 비교용 baseline 재측정을 계획했고 그것이 메모리 부족으로 못 돌아간 항목이다. 지금 말할 수 있는 것은 "검색과 재적재가 둘 다 유의하게 기여한다"까지이고, 어느 쪽이 더 큰지는 **미확정**이다.

**해결안은 제안만 한다(적용하지 않았다 — 지시서 지시).**
- `keep_alive` 로 bge-m3 와 생성모델을 동시 상주시키면 적재 약 9초가 사라질 수 있다. 다만 물리 메모리 7.7 GB 에 gemma2 1.6 GB + bge-m3 1.2 GB 동시 상주는 지금 가용 0.5 GB 상황에서 위험하다 — 메모리 확보가 선행 조건이다.
- 질문 임베딩 결과를 캐시하면 같은 질문의 반복 비용은 사라지지만, 현장 질문은 매번 다르므로 평가셋에서만 효과가 보일 것이다(추정).
- 가장 값싼 쪽은 **R 을 키워드가 없을 때만 쓰는 것**이다 — 판단 요청 1번.

## 지시와 다르게 한 것

1. **R 의 ②를 구현하려고 고정 출처 지름길을 지나쳤다.** `search_sop_documents` 는 사고 종류별 고정 출처가 있으면 임베딩을 아예 건너뛰고 그 문서 청크를 용어 빈도로 고른다. "검색어를 사용자 질문 + `SOP_QUERY[event]` 로" 는 임베딩 검색을 전제하므로, R 에서는 `_search_by_question` 이 `similarity_search` 를 쓴다. 이것이 event_action 문항에도 임베딩 비용(약 7초)을 붙인 원인이다. 코드 주석에 적어 두었다.
2. **`git rm -r` 대신 `git rm -r --cached` 를 썼다.** `git rm -r` 이 하니스 자동승인에 막혔고(Irreversible Local Destruction), 사용자가 직접 실행하기로 했으나 두 번 시도에서 반영되지 않았다. 저장소에서 18개 파일(66,121줄)이 빠지는 결과는 같지만 **작업 폴더의 파일은 디스크에 남아 추적되지 않는 상태**다. 삭제 전 참조 0건과 `radar-guard-hanium/src` 보존을 확인했다.
3. **`baseline_20261001_1911.*` 에 `_절전오염` 을 붙이지 않았다.** LS-05 817.9초 이상치가 있지만 ① 19:11 측정으로 이번 절전(22:30~)과 시간대가 다르고 ② 직전 지시에서 "LS-05: B — 그대로 보존, 대표값 p50" 으로 확정됐고 ③ 커밋된 `보고/ClaudeCode_결과.md` 와 1단계 지시서가 이 경로를 before 근거로 인용한다. 대신 분해용 baseline 을 **새 파일로** 재측정할 계획이었다(메모리 부족으로 미실행).
4. **T-CX03 전제 정정.** 측정 시작 전 사용자에게 적재 완료를 확인받았으나, 이후 "NUL 문자로 적재 실패·중단(`safety_manual_v2` 0개)"이라는 정정을 받았다. 이번 측정은 `collection_name='safety_manual'`(v1, 청크 640개)을 명시해 호출하므로 결과에 영향이 없고, 적재가 중단된 덕에 **Ollama 경합도 없었다.**

## 판단 요청 (사용자·Cowork 가 정할 것)

### 1. 하이브리드 설계안 — T-CC03 에서 Cowork 가 확정 (여기서는 구현·측정하지 않았다)

측정 3개가 가리키는 결론은 "R 의 라우팅은 맞고, R 을 **전체 질문에 적용한 것**과 P 의 적용 조건이 틀렸다"다. 그 둘만 좁히는 설계다.

| 바꿀 곳 | 지금 (R·R+P) | 설계안 | 근거 |
|---|---|---|---|
| 검색 경로 | 모든 질문을 질문 임베딩으로 검색 | `_event_for` 가 **키워드를 찾으면** 1단계 고정 출처 지름길, **못 찾을 때만** 질문 임베딩 검색 | 고정 출처는 event_action 출처 6/6 을 이미 맞히면서 임베딩을 안 써 빠르다. 영향받는 문항이 keyword_free 6개뿐이라 p50 도 기준선에 가깝게 남을 것이다(추정 — 측정 전) |
| 프롬프트 v2 조건 | "검색 결과가 있으면" → R 과 겹쳐 전체 문항에 걸림 | `_event_for` 가 **사고 이벤트를 찾은 경우로 한정** | system_explain 10/11 → 1/11, out_of_scope 거절 5/6 → 1/6 이 전부 이 조건 때문이다. 시스템·범위밖 질문은 v1(SYSTEM_CONTEXT 포함)을 받아야 답할 근거가 있다 |
| `RESPONSE_CATEGORIES` | `00_응급처치_공통`·`01_감전_대응`·`02_협착_예방`·`03_낙상_예방` | 예방 카테고리(`02_협착_예방`·`03_낙상_예방`)를 뺄지 결정 필요 | R 에서 `M-59-2012`(넘어짐 **위험성 평가**)가 사고 대응 답변 근거로 섞여 들어왔다. 1단계 `EVENT_CATEGORY` 주석이 경계한 바로 그 문제다. 다만 빼면 대응 카테고리가 35청크로 줄어 검색 폭이 너무 좁아질 수 있다 |

**이 설계로도 안 풀릴 것**: keyword_free 묶음 통과는 세 변형 모두 0/7 이었다. 검색을 고쳐도 2B 모델이 프롬프트의 안전 규칙을 조치 번호로 베껴 쓴다(KF-01). 라우팅과 별개 문제이므로 모델(Q) 또는 프롬프트 재설계가 따로 필요하다 — 하이브리드만으로 keyword_free 품질이 올라간다고 기대하지 않는 편이 맞다고 본다(추정).

**측정 순서 제안**: 하이브리드 1회 → 그 위에서 Q(3B) 1회 → 분해 비교용 baseline 1회. 각 약 10분이고 Q 는 메모리 2 GB 이상 확보가 선행 조건이다.

### 나머지 판단 요청

## 발견한 문제 (이번 범위 밖)

- **`scripts/sync_agent_docs.py:4` 에 `SyntaxWarning: "\s" is an invalid escape sequence`** 가 뜬다. 지금은 경고지만 향후 파이썬에서 깨진다. docstring 을 raw string 으로 바꾸면 끝난다. 이번 범위가 아니라 고치지 않았다.
- **R 계열에서 `M-59-2012`(넘어짐 위험성 평가) 가 사고 대응 질문에 섞여 들어온다.** `03_낙상_예방` 카테고리를 대응 후보에 넣었기 때문인데, 예방 문서가 사고 대응 답변 근거로 들어가는 것은 1단계 `EVENT_CATEGORY` 주석이 경계한 바로 그 문제다("사고 확정 → 응급처치 문서만"). 하이브리드를 만들 때 `RESPONSE_CATEGORIES` 에서 예방 카테고리를 뺄지 결정해야 한다.
- **`00_응급처치_공통` 이 18청크, `01_감전_대응` 이 17청크뿐이다.** 반면 예방 문서는 `02_협착_예방` 138·`01_감전_예방` 120 이다. 대응 문서가 얇아서 검색 품질이 올라갈 여지가 작다. Codex 의 v2 재적재가 이 비율을 바꾸는지 봐야 한다.
