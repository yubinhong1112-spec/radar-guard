## 지시와 다르게 한 것

1. **메모리 선행 조건 2 GB 를 1.90 GB 에서 시작했다.** 측정값이 샘플마다 ±0.1 GB 흔들리고(직전 관측 0.36 → 0.41 GB) `gemma2:2b` 는 1.6 GB 면 올라가므로, 가장 가벼운 baseline 부터 "죽으면 즉시 멈춤" 조건으로 시작했다. 세 변형 모두 중단 없이 완료했고 `load_duration` p50 0.02초로 스왑 징후도 없다. 측정 후 가용 0.59 GB.
2. **7-1 회귀 확인에 '본문' 비교 기준을 스스로 만들었다.** 지시서는 "기준은 T-CC01 baseline 의 출처·본문" 이라고 했는데, `baseline_20261001_1911.jsonl` 에는 `sources` 만 있고 `context`(본문)가 저장돼 있지 않다. 그래서 세 기준으로 교차 확인했다 — ① 1단계 `sources` ② 컬렉션을 직접 거른 독립 질의의 **본문** ③ v1 단독 640청크 시절 제가 직접 떠본 청크 머리글. 9항목 전부 일치. 다음부터 `context` 도 기록하도록 `chat_eval.py` 를 고치는 편이 좋겠다(이번엔 측정 중 파일을 고칠 수 없어 하지 않았다).
3. **거절 성공을 "미달" 대신 "판정 보류" 로 적었다.** §7-3 대로 LLM 4문항 비교로 판정하면 2/4 vs 4/4 미달이지만, 그 4문항의 프롬프트가 baseline 과 바이트 동일한 것을 확인했으므로 차이가 설계가 아니라 비결정성이다. 사실을 숨기지 않으려고 숫자는 그대로 적고 해석만 보류로 두었다. 어차피 event_action 미달로 최종 판정은 미채택이다.

## 판단 요청 (사용자·Cowork 가 정할 것)

1. **`I+N`(라우터 + `num_predict` 220)을 다음 변형으로 넣을까.** `I` 의 유일한 실질 미달은 event_action 3/12 이고 원인은 6문항 전부 잘린 것이다(eval_count 전부 100). T-CC02 에서 N 은 잘림을 7→4 로 줄였다. 지시서에 없는 변형이라 추가하지 않았다. — **권장: 넣는다.** 측정 1회 약 7분이다. 다만 `I` 의 incident p50 이 이미 11.1초라 N 이 붙으면 15초 조건에 닿을 수 있어, 채택 기준의 incident 상한을 같이 정해 주시면 좋겠다.
2. **안전 규칙을 프롬프트에서 빼고 코드 후처리로 옮길까.** `[지켜야 할 것] … 옮겨 적지 마라` 가 통하지 않았다(EA-06 이 그 두 문장을 1·2번 항목으로 썼다). 2B 모델이 부정 지시를 못 지킨다. A) 안전 규칙을 프롬프트에서 제거하고, 답에 금지 표현이 있으면 코드가 고정 경고로 교체·추가한다 B) 그대로 두고 모델을 바꿀 때 다시 본다. — **권장 A**. 프롬프트로 막는 것은 2B 에서 재현성이 없다.
3. **거절 지표의 측정 신뢰도를 어떻게 올릴까.** out_of_scope LLM 경로가 4문항뿐이라 1건 차이가 25%p 다. A) out_of_scope 문항을 늘린다(예: 12문항) B) 같은 변형을 3회 측정해 중앙값을 쓴다 C) `temperature 0` 로 재서 비결정성을 없앤다. — **권장 C 후 A**. C 는 현행 파라미터 변경이라 before 와 조건이 달라지므로, before 도 `temperature 0` 으로 한 번 다시 재는 비용(약 7분)이 든다.
4. **`I+Q`(qwen2.5:3b) 를 어떻게 다룰까.** 시스템 설명 11/11·p50 4.0초·잘림 1/30 으로 2B 보다 분명히 낫지만, 사고 질문에서 `1`·`4.1.2.1.` 같은 빈 답을 내 event_action 0/12 다. A) 폐기 B) 사고 질문 프롬프트를 3B 에 맞춰 다시 쓴 뒤 재측정 C) 경로별로 모델을 다르게 쓴다(system·other 는 3B, incident 는 2B). — **권장 B**. C 는 모델 두 개를 상주시켜야 해서 지금 메모리(7.7 GB)로는 교대 적재 비용이 돌아온다.
5. **`chat_eval.py` 의 preflight 가 찍는 청크 수를 컬렉션별로 바꿀까.** 지금은 `langchain_pg_embedding` 전체를 세어 "청크 1177개" 로 찍는데, 7-1 수정 후 실제 검색은 `safety_manual` 640청크에만 닿는다. 이 숫자를 보고 v2 혼입을 의심해 한 번 멈춘 적이 있다. — **권장: 바꾼다.** 측정 중에는 파일을 고칠 수 없어 미뤘다.

## 발견한 문제 (이번 범위 밖 — 고치지 않았다)

1. **OS-06 "이 공장 CCTV 영상 보여줘" 가 `system` 으로 분류된다.** `CCTV` 를 시스템 명사 사전에 넣은 탓이다. `system` 은 v1 프롬프트라 동작·점수는 기준선과 같다(실제로 I 에서 거절 True). 라벨만 틀렸다. §7-4 대로 사전을 고치지 않았고 Cowork 가 별도로 다룬다.
2. **LS-01 "쓰러진 뒤 움직임 값이 어느 정도야?" 가 `incident` 로 분류된다 — 수치로 명기(§7-4).** '쓰러' 가 상해 표현이라 라우터는 맞게 동작한 것이고, 이 문항만 v2 프롬프트를 받는다. 결과: `I` 에서 **묶음 1/1 통과, 6.2초, 잘림 없음**(baseline 1/1, 7.7초). live_status 유형 합계도 6/8 로 baseline 과 같다. 조건이 다른데 점수 손해는 없었다.
3. **`scripts/sync_agent_docs.py:4` 의 `SyntaxWarning: "\s" is an invalid escape sequence`** 가 여전하다(T-CC02·T-CC03 두 번째 보고). docstring 을 raw string 으로 바꾸면 끝난다.
4. **`chat_eval.py` 가 `context`(검색된 본문)를 기록하지 않는다.** 그래서 7-1 회귀 확인 때 1단계 본문과 직접 대조할 수 없었다(위 '지시와 다르게 한 것' 2번). 기록하면 파일이 문항당 1.4 KB 늘어난다.
